# NS01-BASELINE — the frozen reference

This directory is the reference every later slice is compared against. Nothing
here is edited to accommodate a change: if a number moves, the change explains
itself or is rejected.

- `environment.txt` — host, toolchain, binary sha256, suite count.
- `full-run.log` — the complete battery run, verbatim, failures included.
- `performance.md` — machine-generated by `test/perf_baseline.py`. Regenerate
  it, do not hand-edit it.

## Behaviour baseline

99 suites, **93 pass / 6 fail**, 1369.3 s, at commit `58384f8`.

The suite count grew from main's 94 as this work added guards: the suite
manifest, the wire constants, the fixture reaping, the architecture boundary
and the terminal replies. The binaries were verified unchanged across the run
(`sha256_test` in `environment.txt` matches the tree), because an earlier
attempt was invalidated by rebuilding mid-run and had to be discarded.

The six failures are **pre-existing on this branch**, proven rather than
assumed: each was re-run at `a7ae1a5` (before the fixture work landed) with the
same binaries in an isolated worktree, and each failed there with the same
check names.

## Performance baseline — what it already proves

Numbers in `performance.md`. Two things are settled by measurement rather than
by reading the source:

**1. Cost follows changed cells, not desktop area — confirmed.** Across a 13x
growth in area (3 000 -> 40 000 cells), the client emits the *same* 94 bytes
and the *same* 24 changed cells per painted frame. That is the Main+ invariant,
and it is why this architecture was kept.

**2. The full-surface scan does NOT follow changed cells — quantified.**

| geometry | cells | `frame-compare` avg | key echo p50 |
| --- | ---: | ---: | ---: |
| 100x30 | 3 000 | 191 us | 13.3 ms |
| 200x50 | 10 000 | 330 us | 15.4 ms |
| 400x100 | 40 000 | 1 797 us | 17.1 ms |

The scan grows ~9.4x while the emitted bytes stay flat, because
`WideUpdateScreen` compares every cell on every frame regardless of what
changed. This turns the source-level claim into a fact and sizes the work:

- **The scan is not what the user feels today.** 1.8 ms of scan sits inside a
  ~17 ms round trip, so the dominant cost is elsewhere — the fixed ~10 ms idle
  sleep in the vendored `GiveUpTimeSlice` plus the coalescing window. That is
  milestone **NS05-I1** (event-driven wake), and it is correctly ordered first.
- **After NS05-I1 lands, the scan becomes the next ceiling**, and it is what
  **NS05-I3** (damage tracking) exists to remove. NS05-I3 must not be judged on
  100x30, where it can only lose; its case is 400x100 and above.

Percentiles come from a power-of-two histogram, so `p50_le_us` is an upper
bucket bound: read them as "at or below", never as exact times.

## The telemetry costs the release binary nothing — proven, not measured

Instrumentation was first added to `WideUpdateScreen` behind a runtime check.
Two honest A/B runs against a binary built without it **disagreed**: +1.4% at
100x30 in the first, +27% in the second, because run-to-run variance of the
*same* binary (17.1 ms then 14.5 ms) was larger than the effect being measured.
A measurement that cannot resolve the question does not settle it.

So the instrumentation moved behind `{$IFDEF SUPERTERM_PERF_BUILD}` and into a
separate `make perf` binary, exactly as `debug-heap` already does for heap
tracing. The claim is now checkable without any timing at all: building this
tree twice in the same directory with the same flags, once with the
pre-instrumentation `st_video.pas` and once with the current one, produces a
**byte-identical `.text` section** — 1 870 944 bytes, same SHA-256. Whole-file
identity is not the test, because `-gl` embeds line numbers and the added
comments move them.

`bin/superterm` and `bin/superterm-test` contain no telemetry code, no guarded
branch and no unit initializer; `bin/superterm-perf` carries it. Point
`perf_baseline.py` at the perf binary — it refuses to run otherwise.

## Reproducing

```sh
make release test-runtime            # never test inherited binaries
python3 test/run_tests.py --project-dir . $(all suites)   # behaviour
python3 test/perf_baseline.py        # performance, rewrites performance.md
```

`perf_baseline.py` is deliberately not a `*_test.py`: it measures, it does not
assert. A timing threshold inside the battery would be a flake generator on a
loaded machine. Comparing two runs of this table is a human decision, governed
by the gate in the plan: reject a slice when p50 or p95 exceeds this baseline
by more than `max(1 ms, 5%)` on two repeat runs, when bytes per frame grow
without a required new effect, or when scaling with desktop area worsens.
